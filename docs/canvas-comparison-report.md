## 结论

**没有足够的正向证据支持改回 React Flow；但这不是因为迁移麻烦，而是对照结果显示各方案的优势取决于呈现方式和操作类型，没有出现适用于当前产品约束的全面优胜者。**

本轮最明确的两个优化方向是：

1. 普通内容的持续缩放，优先验证并局部采用 `transform`，不把浏览器和所有编辑器一并改掉。
2. 运行态保存先跳过未变化实体的重复序列化；这个方向比把完整对象往返搬到另一个进程更贴近当前代码中的成本来源。

继续保留按节点 pin 的虚拟化。不要直接采用“流式期间全量挂载”、全局单层 transform、全部任务搬进独立进程，或默认双段镜头动画。

**本轮没有修改产品实现、生产依赖或用户数据，也没有调用真实模型服务。新增内容只有独立实验、原始记录和本报告。**

## 3. 框架与呈现架构对照

300 节点，帧 P95 中位数，单位 ms：

| 简化原型 | 平移 | 缩放 | 同时移动 20 节点 |
| --- | ---: | ---: | ---: |
| 当前方式模型：逐节点定位 + 内容 zoom | 12.5 | 50.1 | 4.3 |
| 共享世界 transform | 45.8 | 54.2 | 50.0 |
| React Flow 11.11.4，内容在变换树内 | 20.8 | 33.3 | 79.2 |
| React Flow 壳 + 树外抬升内容 | 8.3 | 54.2 | 33.4 |

公平性修正包括：稳定未变化节点的 data 引用、稳定 edge 数组、记忆化节点正文；检查确认四种模型拖拽时都仅产生 `20×45=900` 次正文渲染，而不是让 React Flow 无端重画所有 300 个正文。

**解释与决策：**

- React Flow 的普通方案在这个缩放样本中确实优于当前方式模型；不能否认其局部优势。
- 采用内容抬升以后，该样本的缩放优势没有保留，但平移更快。这说明内容呈现策略是关键变量。
- React Flow 没有在所有操作中占优；多选更新尤其不能只看平移结果代替判断。
- 共享 transform 的布局耗时接近零，但整体帧间隔仍可能更差。**减少布局不等于消除绘制与合成成本**，在本机软件合成环境中尤其明显。
- **不采纳框架迁移。**采纳其可验证的局部机制不需要恢复旧业务结构。若继续研究迁移，应比较保留相同 BrowserContent、编辑器、菜单、历史、层叠和持久化语义的实现，而不能把精简样例快于完整产品作为证据。

## 4. CSS zoom 与 transform

300 个富内容样本节点，持续缩放：

| 指标 | zoom | transform |
| --- | ---: | ---: |
| 45 次更新的总布局耗时 | 1002.4 ms | 43.2 ms |
| 总任务耗时 | 2209.2 ms | 354.7 ms |
| 帧 P95 中位数 | 58.3 ms | 14.0 ms |

布局耗时约下降 **95.7%**。五次布局耗时范围分别为 948.0–1496.2 ms 和 24.7–49.9 ms，明显超过本轮运行波动。

但固定倍率平移没有相同收益：两种方案的布局耗时都约 1 ms 或以下，transform 的总任务耗时在该样本中反而略高。不能把缩放结果推广成所有操作都变快。

**决策：局部采纳方向明确。**先用于普通展示内容的缩放呈现；保留浏览器专用策略，编辑器与弹出菜单通过对应兼容性测试后再扩展。不要直接把所有节点塞进同一个巨大缩放层。

## 6. 流式通道：常规输出与突发吞吐分开判断

每个逻辑记录约 4 KiB，下面是通道交付延迟，不包含 Markdown 渲染：

| 场景/指标 | 拉取式 IPC | MessagePort | 本地 HTTP |
| --- | ---: | ---: | ---: |
| 60 条/秒，交付延迟 P95 | 1.01 ms | 0.71 ms | 1.11 ms |
| 256 条突发记录，总完成耗时 | 180.5 ms | 64.7 ms | 48.2 ms |

总完成耗时包含三个方案相同的约 30 ms 源启动等待。跨进程高精度时间戳存在小误差，不能把亚毫秒差异包装为明显的用户体验提升。

**决策：**

- 日常 token 节奏下，没有证据支持为降低可感知延迟切换到本地 HTTP。
- 突发吞吐下，两种持续通道都明显胜过逐条拉取；本样本中 HTTP 吞吐最好，MessagePort 其次。
- 该测试的 IPC/MessagePort 按固定逻辑记录传递，HTTP 可以自行合包；收益包含合包效应，不能全部归因于协议名称。生产选型还需要对照批量 IPC/MessagePort，而非直接新增全局代理。
- 可以将 MessagePort/HTTP 保留为**吞吐型数据通道候选**，不据此重写所有普通 AI 请求。密钥隔离和主进程控制面保持独立要求。

## 7. Worker、独立进程与更直接的根因

完整对象输入并返回完整序列化结果，32 MiB 样本：

| 执行位置 | 总完成耗时 | 主线程探针最大间隔 |
| --- | ---: | ---: |
| 渲染线程 | 62.1 ms | 62.4 ms |
| Web Worker | 180.2 ms | 40.3 ms |
| utility process | 703.8 ms | 103.2 ms |

8 MiB 时，渲染线程/Worker 总耗时约 10.6/49.3 ms，探针间隔约 11.1/12.4 ms，Worker 也没有显示稳定响应收益。

**解释：**Worker 在较大样本中降低了主线程阻塞，但增加了完成时间；完整对象往返 utility process 在本测试中两项都变差。独立进程是否更合适取决于数据所有权与通信粒度，不能认为“换一个进程运行相同函数”必然更快。当前桌面存储已有原生路径，也不是所有存储 I/O 都发生在 renderer。

### 补充发现：目前先序列化，再比较是否变化

检查 `runtime-persistence.ts` 的 `persistSnapshot` 可见：先调用 `serializeCollectionEntity`，再与 `lastSerialized` 比较。这避免了相同内容重复落盘，但没有避免重复序列化的 CPU 成本。

补充实验直接提取当前 `serializeEntity`，对不可变 AI 会话形状比较“现状”与“引用未变化就跳过”的原型。五次中位数：

| 总会话工作集，仅一个实体变化 | 当前序列化后比较 | 先判断引用 |
| --- | ---: | ---: |
| 1 MiB | 0.8375 ms | 0.0075 ms |
| 8 MiB | 6.5713 ms | 0.0659 ms |
| 32 MiB | 30.2728 ms | 0.3786 ms |

90 项检查得到一致的写入意图。全部实体变化时仍然要全部序列化，没有数量级优势。

这是 **Node CPU 内核实验**，不是整个持久化链路或 Electron 帧率结果。但它为一个更直接的优化提供了证据：先消除重复工作，再决定是否迁移线程。

**决策：优先采用增量序列化方向；Worker 作为大任务条件方案；不整体搬迁任务到独立进程。**落地必须验证缓存的加载/删除失效、写入失败重试，以及只在成功保存后更新缓存；本轮原型仅覆盖不可变 AI 会话，不推定适用于所有运行态集合。

## 8. 动画与背景材质

2000 世界单位导航，固定参数模拟，进入位置/速度容差的时间：

| 策略 | 稳定时间 | 特点 |
| --- | ---: | --- |
| 220ms 短缓动 | 约 221 ms | 完成快；重新启动曲线时速度可能跳变 |
| 临界阻尼弹簧 | 约 746 ms | 本参数无过冲，改目标时保留速度 |
| stiffness=250 / damping=25 | 约 625 ms | 本样本过冲约 25.2 世界单位 |
| 400ms 居中，再 680ms 推近 | 约 1046 ms | 对目标有强调，但日常定位占用时间更长 |

40 个改目标/取消场景通过，包括取消后不能被延迟的第二段再次推动镜头。固定时长段使用 cubic-out 是实验假设；原文没有给出其真实 easing。不能把此模拟说成复现了 Creatos 的实际动画引擎。

**决策：日常程序化定位优先短且可中断；连续重定位可选保留速度的弹簧；不把双段推近作为默认导航。**优先级来源是定位完成时间、连续性和过冲，而不是动效库体积或实现成本。舒适度偏好仍需要人判断。

300 节点平移的总任务耗时：纯色约 212.7 ms，轻渐变 310.1 ms，噪声 244.5 ms，组合 242.5 ms。五次范围显著重叠，**不能据此稳定排列材质性能，也不能自动判定哪个更好看**。

材质保持可选候选，不把它列为性能收益项；网点跟随世界坐标的需求与材质选择分开处理。

## 9. 一个没有测出提速的项目：批量节点更新

真实 CanvasViewport 参照中，每帧移动 20 个节点，45 帧：

- 单节点逐次更新：900 次图状态通知。
- 等价批量原型：45 次通知，减少 95%；每一帧的位置一致性检查通过。
- 300 节点时，更新调用 P95 中位数分别为 25.3 ms 与 39.5 ms；批量原型没有更快。
- 批量组波动也更大：22.0–46.1 ms，当前方式约 22.3–27.3 ms。

**决策：不能把“通知减少 95%”写成“性能提高 95%”。**批量写入的原子性和减少通知有结构价值，但这个原型不能作为已经验证的提速方案。优先检查订阅范围、节点壳与上下文更新等剩余成本，而不是直接根据操作次数上线替换。

## 10. 根据证据调整的实施顺序

后续执行回到原《Cnote 画布体验优化计划》的四部分与阶段结构，仓库同步副本为 `canvas-optimization-plan.md`：基线 → 手势与流式合批候选验证 → 视口及订阅隔离 → 上游输入契约 → 网点与导航。增量序列化补入 P1，局部缩放与生命周期补入 P2；不再使用另起的 P0–P5 路线。以下为实测支持的局部方向，不替代原计划的阶段安排，也不表示产品改动已完成。

1. **增量序列化**：对不可变会话避免重复编码，补全失效与失败重试测试。
2. **普通内容的局部 transform**：先非编辑展示内容，再单独验证编辑器、菜单与浏览器。
3. **订阅/节点壳更新隔离**：保留当前框架、runtime 和按节点 pin；不要用一个巨大共享层代替分析剩余成本。
4. **按负载选择数据通道和 Worker**：常规请求保持现状；明确出现突发吞吐或大序列化任务时再应用对应方案。
5. **短且可中断的导航**：动画、材质与性能优化分开交付。

React Flow 迁移、流式期间全局关闭虚拟化、全量独立进程迁移和默认双段推近，不进入本轮实施清单。这个结论来自适用边界与对照结果，不来自“更麻烦”。
