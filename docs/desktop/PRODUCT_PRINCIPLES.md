# Desktop 产品原则

## 1. 产品定位

Cnote 是一个本地优先的研究、创作和自动化工作台，桌面端组合以下能力：

- 可视化工作流编排
- 原生浏览器研究空间
- 内容捕获、解析和结构化
- AI 与本地工具调用
- 本地资源管理
- 可恢复的后台任务
- 输出编辑和发布

核心循环是：

```text
发现 → 浏览与捕获 → 解析与整理 → 连接上下文 → AI/工具处理 → 人工编辑 → 自动化输出
```

画布是重要工作面，但不是产品唯一的中心。

## 2. Desktop 是权威产品

桌面端拥有完整能力和最终产品语义。Web 版用于快速体验、分享、兼容和反馈收集，不应反过来限制桌面端。

当某个能力无法在 Web 中可靠实现时，Web 可以：

- 提供降级实现；
- 保留数据和操作入口；
- 明确提示需要 Desktop；
- 使用远程服务作为 fallback。

不允许为了保持两端表面一致而削弱 Desktop。

## 3. 解除 Cnote 自己造成的限制

Desktop 应最大限度摆脱浏览器运行时带来的限制，包括：

- CORS 和渲染层网络限制；
- iframe 的嵌入、跨域和导航限制；
- 浏览器文件访问和下载限制；
- 页面生命周期导致的任务中断；
- IndexedDB 不适合大规模本地资源的限制；
- 渲染层保存密钥的安全限制；
- 浏览器无法直接调用本地工具和操作系统能力的限制。

“解除限制”不等于绕过第三方授权、验证码、DRM、服务商配额或法律边界。产品目标是：在用户有权访问且操作系统允许的范围内，不因为 Cnote 的 Web 架构而主动降低能力。

## 4. 本地能力优先

如果能力可以在用户设备上可靠完成，Desktop 默认优先本地完成：

- API 请求优先由受控的本地网络层发起；
- 页面解析优先使用本地请求、渲染页面或本地解析器；
- 大文件优先进入本地文件系统；
- 长任务进入本地任务队列；
- 本地模型、OCR、ASR、FFmpeg 和脚本工具可以作为能力提供者。

远程 Worker 的角色是 Web 端必需服务、跨设备 fallback、共享部署选项和可选的远程计算，不是 Desktop 的默认依赖。

## 5. 浏览器是第一类产品能力

浏览器节点不能被理解为“显示一个网页的卡片”。浏览器应该拥有独立会话、导航、登录态、下载、弹窗、页面快照和 DOM 操作语义。

浏览器会话与 Flow 节点分离：节点引用会话和捕获结果，会话本身可以被多个任务复用，也可以按用户要求隔离。

## 6. 内容必须可追溯

任何进入 Flow 的内容都应该保留来源和处理过程。内容对象应尽量包含：

- 原始地址和最终地址；
- 捕获时间；
- 原始页面或文件快照；
- 解析后的正文和结构；
- 媒体与附件引用；
- 内容哈希；
- 解析器和版本；
- 处理警告与失败原因。

AI 输出需要能够回溯到输入内容，而不是只留下不可解释的文本。

## 7. 任务必须可恢复

用户不应该因为关闭窗口、切换页面或短暂网络错误而丢失长任务。任务系统必须支持：

- 持久化状态；
- 检查点；
- 取消和重试；
- 超时；
- 并行和队列；
- 应用重启后的恢复策略；
- 人工介入和错误记录。

## 8. 数据本地优先，但必须可迁移

用户数据默认保存在本机，不依赖账户和中心服务器。与此同时，数据必须具备稳定的版本化导入导出能力。

现有 `.cnote.zip` 应继续演进为 Web 与 Desktop 的标准交换格式；GitHub 只同步代码，不同步用户 Flow、密钥、Cookie 或本地资源。

## 9. 安全边界优先于便利

桌面端拥有更高能力，因此必须增加而不是减少安全边界：

- 远程页面不能访问主进程能力；
- API Key 不进入不可信页面和普通渲染上下文；
- 插件、脚本和外部工具采用权限声明；
- 文件、网络、剪贴板和系统调用可审计；
- 浏览器会话与 Cnote 主应用隔离；
- 高风险操作需要明确授权。

## 10. 能力应可扩展

节点、解析器、模型提供者、浏览器脚本和输出适配器都不应永久写死在一个大型条件分支中。未来应通过注册表、版本化契约和受控插件扩展。

扩展能力必须包含：

- 唯一标识和版本；
- 输入输出 schema；
- 权限声明；
- 配置迁移；
- 错误和兼容性信息。

## 11. 性能以桌面工作负载为目标

桌面端需要为大型 Flow、大量资源、多浏览器会话和后台任务设计：

- 画布虚拟化和增量更新；
- 资源按需加载；
- 页面和任务隔离；
- 内存和 CPU 预算；
- 崩溃恢复；
- 长任务日志和诊断。

不能继续以“小型 Web Demo 能运行”作为性能标准。

## 12. 渐进式实现，不渐进式妥协

实现可以分阶段，但最终能力方向不能被当前 Web 实现锁死。每个阶段都应该优先验证桌面端最具差异化的垂直切片，而不是先复制完整 Web 页面。

推荐的第一个垂直切片：

```text
原生浏览器会话 → 页面捕获 → 本地内容解析 → AI 请求 → Flow 运行 → 可恢复任务
```
